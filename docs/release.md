# Releasing Rosalena Harness

This is the runbook for turning the source in this repository into an installer somebody can
download, and for keeping the download page truthful about what exists.

**Status today: nothing has been released.** No release workflow has ever run, no tag exists, and
no user has a Windows installer or a macOS `.dmg`. The download page says so, because the manifest
it reads marks all six artifacts `available: false`. A macOS artifact cannot exist at all until a
macOS runner produces one: everything below about macOS is a described plan plus the exact
commands, not a report of a build.

---

## 1. What the pipeline is

```
tag v* / manual dispatch
        │
        ├─ gate     ubuntu-latest   engine tests, site tests, config checks, staged router
        │                            really starts, manifest cannot lie
        │
        ├─ windows  windows-latest  stage → electron-builder (nsis + portable) → verify → upload
        │
        └─ macos    macos-14        stage → electron-builder (dmg + zip, arm64 + x64) → verify → upload
                        │
                     release    ubuntu-latest  download artifacts → manifest.mjs → GitHub Release
```

The Windows and macOS jobs run in parallel after the gate. The release job runs only when Windows
succeeded; the macOS job is allowed to fail the run without destroying the Windows artifacts, and
when that happens the manifest simply marks the macOS entries unavailable.

## 2. Files

| Path | Role |
| --- | --- |
| `.github/workflows/release.yml` | the four jobs above |
| `packaging/release/electron-builder.win.yml` | nsis installer + portable exe, x64 |
| `packaging/release/electron-builder.mac.yml` | dmg + zip, arm64 + x64, hardened runtime, `identity: null` |
| `packaging/release/entitlements.mac.plist` | entitlements for the hardened runtime |
| `packaging/release/stage.mjs` | assembles `build/release/app` (the app plus the trees it imports) |

| `packaging/release/build.mjs` | runs electron-builder against a staged app and prints sizes and SHA-256 |
| `packaging/release/manifest.mjs` | turns real artifacts into `releases.json` and `SHA256SUMS.txt` |
| `packaging/release/check-config.mjs` | parses both YAML configs and asserts the invariants |
| `packaging/release/README.md` | the resource map, the secrets table, the blocker list |
| `packaging/release/NOTARIZATION.md` | signing and notarization, step by step |

| `site/public/download/index.html` + `download.js` | the download page |
| `site/test/download.test.mjs` | tests that the manifest and the page stay honest |
| `docs/download-page.png` | screenshot of the page in its current state |

`desktop/package.json` is not modified by any of this: electron-builder is configured entirely
from `packaging/release/`, and the staged app's `package.json` is generated by `stage.mjs`.

## 3. One-time setup

```powershell
cd packaging/release
npm install          # electron + electron-builder, dev dependencies only, ~1 minute
```

The app itself still has zero runtime dependencies. Nothing from `node_modules` is ever shipped:
both configs exclude `**/node_modules/**` and only copy explicit files and trees.

## 4. Build the Windows artifacts on this machine

```powershell
cd packaging/release
node stage.mjs --check                 # resource map only, no writes
node stage.mjs                         # writes build/release/app
node build.mjs win                     # nsis installer + portable exe, x64
node check-config.mjs                  # optional: YAML invariants, prints passed/failed
```

`build.mjs` prints every artifact with its byte size and SHA-256. Then install the `.exe` on a
clean Windows box and confirm the window opens and the model picker fills.

A local build is unsigned unless a certificate is supplied:

```powershell
node build.mjs win --sign "CN=Your Name, O=Your Company"   # needs a real certificate in the store
```

## 5. macOS

A `.dmg` cannot be built on Windows. `build.mjs mac` refuses to run unless `process.platform`
is `darwin`. The only way to get a macOS artifact is the `macos` job in the workflow, on a
GitHub-hosted `macos-14` runner (Apple silicon), producing both architectures from that one job:

- `Rosalena-Harness-<version>-arm64.dmg` and `...-arm64.zip`
- `Rosalena-Harness-<version>-x64.dmg` and `...-x64.zip`

One job rather than two (an extra `macos-13` job for Intel) because electron-builder cross-compiles
the Intel bundle fine from Apple silicon when no native modules are involved, which is the case
here: the app is pure JavaScript and the only binary is Electron's own prebuilt one. A second
runner would double the paid minutes for a file that would be byte-identical in behaviour.

The build is **unsigned** by default (`identity: null`, `notarize: false`). On a Mac that means
Gatekeeper quarantine and one command on first launch:

```bash
xattr -dr com.apple.quarantine "/Applications/Rosalena Harness.app"
```

If the `APPLE_*` secrets and `MAC_CERT_P12` are set, the workflow signs, notarizes and validates
instead, and the command above is unnecessary. `NOTARIZATION.md` has the full procedure, the
required Apple account type and the common rejection causes.

## 6. Cut a release

1. Bump the version in `desktop/package.json` (`version`). It is the single source of truth;
   `stage.mjs` reads it, and both configs stamp it into artifact names.
2. Run the gate locally so CI does not find it first:

   ```bash
   cd harness && node --import ./test/isolate.mjs --test
   cd ../site && node --test test/*.test.mjs
   cd .. && node packaging/release/stage.mjs && node packaging/release/check-router-spawn.mjs
   ```

3. Commit, then tag and push the tag:

   ```bash
   git tag v0.2.0 && git push origin v0.2.0
   ```

   The tag drives everything. A manual dispatch (`Actions → release → Run workflow`) also works:
   it takes an optional `version` and a `publish` boolean, and with `publish` off it runs the whole
   build but stops before touching a GitHub Release, which is how you test the pipeline.
4. Watch the four jobs. The `gate` job fails fast on a red test, which is the point of building
   nothing when the engine tests fail.
5. When `release` finishes, the GitHub Release exists with all artifacts, `releases.json` and
   `SHA256SUMS.txt` attached, and a table in the step summary.
6. Update the download page (§7), which is a separate, deliberate commit. The pipeline does not
   push to the site: a machine that can publish an installer should not be able to rewrite the
   page that describes it without a human review.
7. Check the page on a real phone and a real desktop, with the network throttled, and confirm the
   sizes and checksums shown match the files you just downloaded.

## 7. Update the download page

The page reads `site/public/download/releases.json` at load time and renders one card per platform
plus one table row per file. To move it from "not built yet" to a real download:

```bash
# artifacts/ holds the files you downloaded from the GitHub Release
node packaging/release/manifest.mjs \
  --dir artifacts \
  --version 0.2.0 \
  --base-url https://github.com/<owner>/<repo>/releases/download/v0.2.0 \
  --out site/public/download/releases.json
```

`manifest.mjs` measures each file it finds: the size and the SHA-256 come from the bytes on disk,
never from a number typed by hand. An artifact only becomes `available: true` when a file matched
**and** a `--base-url` was given, because a build you cannot link to is not a download. Run the
site tests afterwards:

```bash
cd site && node --test test/*.test.mjs
```

`site/test/download.test.mjs` refuses a manifest that claims a file without a url, a size or a
64-hex checksum, and refuses a page that hardcodes an artifact link. If a test fails after you
regenerate the manifest, the manifest is wrong, not the test.

### The update feed is the other half

Installed apps read a second committed file, `site/public/download/updates.json`, to answer "am I
current?". It is written from the same measured artifacts, in the same step of the release job:

```bash
node packaging/release/manifest.mjs --updates \
  --dir artifacts \
  --version 0.2.0 \
  --release-url https://github.com/<owner>/<repo>/releases/tag/v0.2.0 \
  --notes NOTES.md \
  --out site/public/download/updates.json
```

Commit it together with `releases.json`: the page and the app describe the same release, and a feed
that names a version the page does not list is a page and a program that disagree. `--updates`
refuses to write anything when `--dir` held no artifact or when no release page was given, and it
runs the app's own validator before writing. See `updates.md` for the field-by-field rules, the three
answers the app can give, and the window wiring that is still outstanding.

## 8. Verify a download

```powershell
Get-FileHash -Algorithm SHA256 .\Rosalena-Harness-Setup-0.2.0-x64.exe
```

```bash
shasum -a 256 ./Rosalena-Harness-0.2.0-arm64.dmg     # macOS
sha256sum ./Rosalena-Harness-0.2.0-arm64.dmg         # Linux
```

Compare against the SHA-256 the page shows. If they differ, do not run the file: the checksum on
the page is the one the pipeline measured from the file it published.

## 9. Secrets

Set these in `Settings → Secrets and variables → Actions`. All are optional; without them the
build is unsigned and the workflow still produces artifacts.

| Secret | Used for |
| --- | --- |
| `WIN_CERT_PFX` | base64 of a Windows code-signing certificate (`.pfx`) |
| `WIN_CERT_PASSWORD` | password for that `.pfx` |
| `MAC_CERT_P12` | base64 of a Developer ID Application certificate |
| `MAC_CERT_PASSWORD` | password for that `.p12` |
| `MAC_SIGN_IDENTITY` | exact identity string, for example `Developer ID Application: Your Name (TEAMID)` |
| `APPLE_ID` | Apple account email used for notarization |
| `APPLE_APP_SPECIFIC_PASSWORD` | app-specific password for that account |
| `APPLE_TEAM_ID` | ten-character team identifier |

The macOS job decides between the signed and the unsigned path from one job-level environment
variable, because a step `if:` cannot read `secrets` directly. If `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`,
`APPLE_TEAM_ID`, `MAC_CERT_P12` and `MAC_CERT_PASSWORD` are all non-empty, it runs the signed
build and validates the notarization; otherwise it runs the unsigned build and says so in the log.

## 10. What is still missing before a Mac user can install

Short version, because the page says it too:

- **No macOS build has ever been produced.** The job is written and every input it consumes is
  checked on a clean machine, but a `/Applications` folder has never seen this app, and no `.dmg`
  has ever been opened. Nothing in this document is a report of a build.
- **Unsigned and un-notarized** until the Apple secrets exist. The first launch needs
  `xattr -dr com.apple.quarantine "/Applications/Rosalena Harness.app"`, and macOS 15 additionally
  needs System Settings → Privacy & Security → "Open Anyway".
- **The Mac window itself is unverified.** The code now asks for `titleBarStyle: "hiddenInset"`
  with a real frame on darwin (traffic lights, native drag and zoom) and hides the page's own
  window buttons there, but nobody has looked at it on a Mac. Same for the macOS menu bar
  (About / Services / Hide / Quit, Edit with the clipboard roles, View, Window), the Dock icon and
  the `activate`-reopens-the-window behaviour.
- **The router start is verified on Windows and Linux, not on a Mac.** `desktop/router-supervisor.mjs`
  starts `<resources>/router/src/index.mjs` with the bundle's own binary
  (`ELECTRON_RUN_AS_NODE=1`), waits for `GET /v1/models`, moves the ledger, usage log, request logs
  and key file into `~/Library/Application Support/Rosalena Harness/router/` via
  `ROSALENA_ROUTER_STATE_DIR`, and reuses a router that is already listening. What is unverified is
  whether `spawn` of `process.execPath` inside a signed/translocated `.app` is allowed by the
  hardened runtime on a real Mac — the first thing to test when someone finally runs the job.
- **Voice input is absent on macOS, deliberately.** The capture path is Windows-only; every backend
  reports itself unavailable off Windows instead of failing at the microphone, and the window
  exposes no microphone control, so nothing is left dangling.
- **`run_command` and plugin tools still need system binaries** (`node`, `python`, `ffmpeg`) on
  `PATH`. The router no longer does, which was the one that broke a fresh install.

`packaging/release/README.md` §5.2 lists what remains, with the exact file each item touches.
§5.1 lists what was fixed and how each fix was checked.

## 11. Rules for maintainers

1. **Never hand-edit `releases.json` to set `available: true`.** Regenerate it with
   `manifest.mjs` against files that exist.
2. **Never add a download link to `index.html`.** Links come from the manifest at runtime, which
   is the only way the page cannot 404.
3. **Never merge a manifest entry with a made-up size or hash.** An unknown size is `0` and an
   unknown hash is `""`; the page renders those as `-` and `checksum pending`.
4. **If a build is broken, say so on the page.** The honest version of this page is more useful
   than a download button that fails after 400 MB.
5. **Do not describe a workflow as if it had run.** An unrun workflow is a plan.

## 12. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `build.mjs mac` exits with "can only be built on macOS" | expected on Windows; use the workflow |
| `stage.mjs --check` reports a missing path | a file moved; fix the resource map in `stage.mjs` and both configs |
| `check-config.mjs` fails on `artifactName` | it must be stamped with `${version}` and `${arch}` |
| the page shows "The build manifest could not be loaded" | `releases.json` is missing, not valid JSON, or served with the wrong content type |
| the page shows every file as "not built yet" after a release | the manifest was not regenerated with `--base-url` |
| the macOS job fails at signing | wrong identity string, or the `.p12` is not a Developer ID Application certificate |
| the macOS job fails at notarization | see the rejection causes in `NOTARIZATION.md`; the log has the notarytool message |
